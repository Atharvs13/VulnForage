# Lab authoring and HTTP testing

## Module convention

Add a lab below its OWASP category in `src/modules/labs/`. Keep its route,
controller, service, and short README together. The controller should translate
HTTP input/output only; the service owns the deliberately flawed application
logic and SQLite interaction. Never import a vulnerable service from a core
route or service.

Register the lab in `src/lab/lab.registry.ts` with a stable ID, OWASP category,
difficulty, endpoints, objectives, prerequisite knowledge, exploit event types,
and reset strategy. Add deterministic fixtures only when state is necessary.
Implement reset in `src/lab/lab.reset.ts`, record exploit proof with
`recordLabEvent`, and add a mission seed whose ID matches `missionId`.

Lab events may contain object IDs, synthetic owner/role identifiers, request
metadata, and the observed state transition. They must never contain passwords,
authorization headers, cookies, session IDs, private keys, tokens, or real
secrets. Evidence follows the same restriction.

Every lab needs tests for its baseline, intended vulnerable behavior, event,
mission validation where applicable, safety boundary, and deterministic reset.

## A01 curl flow

Start the backend, then use a cookie jar:

```bash
curl -sS -c /tmp/vf-cookie.txt \
  -H 'Content-Type: application/json' \
  -d '{"email":"user1@vulnforge.local","password":"User1Lab!"}' \
  http://localhost:4000/api/auth/login

curl -sS -b /tmp/vf-cookie.txt http://localhost:4000/api/orders/1001
curl -sS -b /tmp/vf-cookie.txt http://localhost:4000/api/orders/1002
curl -sS -b /tmp/vf-cookie.txt http://localhost:4000/api/lab/orders/1002
```

The second core request returns `404 ORDER_NOT_FOUND`; the lab request returns
synthetic order `1002` and records `LAB_A01_BOLA_EXPLOITED`.

For the nested and role-confusion variants:

```bash
curl -sS -b /tmp/vf-cookie.txt \
  http://localhost:4000/api/lab/users/1/orders/1002

curl -sS -b /tmp/vf-cookie.txt \
  'http://localhost:4000/api/lab/access/roles?page=1&pageSize=10&sort=name'

curl -sS -b /tmp/vf-cookie.txt \
  'http://localhost:4000/api/lab/access/resources?scope=catalog'

curl -sS -b /tmp/vf-cookie.txt -X PATCH \
  -H 'Content-Type: application/json' -H 'X-Lab-Role-Id: 999' \
  -d '{"classification":"public"}' \
  http://localhost:4000/api/lab/access/resources/7002
```

## Burp Suite or ZAP flow

Configure the browser to use the proxy, sign in with a seeded synthetic account,
and keep the `vf_session` cookie generated by the backend. Browse the secure core
endpoint first. Send the captured request to Repeater, change only the relevant
path/query/body/header value, and direct the request to the documented lab route.
Do not paste cookies or authorization tokens into mission evidence.

For A01 Easy, compare order IDs `1001` and `1002`. For Medium, keep `userId=1`
and change `orderId`. For Hard, first inspect the paginated role and resource
catalogs, then add `X-Lab-Role-Id` and change the JSON `classification` field.
Submit a concise observation and, optionally, the event ID shown by an authorized
admin log view. Reset only the relevant lab before repeating an exercise.

The SSRF lab has exactly one in-process target and performs no network fetch.
The SQL injection lab copies only its dedicated fixtures into a short-lived
SQLite database, preventing UNION payloads from reaching core session/user data.
Uploads are random-named, size-limited, stored outside source directories, and
served as non-executable text.
